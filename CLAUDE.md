# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository layout

- `Trailmap App/` — the active app under development: `index.html` (markup, CSS, all JS logic) plus `sw.js` (service worker) plus `regions/*.json` (one file per region group, lazily fetched — see Architecture below). Multi-region by design and built to keep scaling as more regions are added: currently covers Paznaun and 3-Länder Enduro Trails, each broken into several sub-regions/hubs, with a growing list of future regions expected. No build step, no bundler, no framework, no `package.json`.
- `Paznaun App/` — the original, single-region Paznaun app (Ischgl/Samnaun, Kappl, Galtür). Kept as-is/untouched; not the one to extend with new regions. `Trailmap App/index.html` started as a copy of this file's structure (CSS/JS architecture, PWA meta tags, service worker), then had the two-level region layer and additional regions added. `Paznaun App/trail-map-app-summary.md` — a detailed (German) design/lessons-learned writeup — applies equally to `Trailmap App/`, since the two share the same UI/JS architecture; **read it before making non-trivial changes to either app's `index.html`**. Do not silently "simplify away" something that looks odd there without checking this doc first.
- `Material/Paznaun/` — raw GPX source files for the Paznaun region trails.
- `Material/3-Laender-Enduro-Trails/` — raw GPX source files for the 3-Länder Enduro Trails region (Nauders am Reschenpass: Mutzkopf/Bergkastel/Schöneben/Haideralm hubs), plus `BiketrailsNauders.pdf`, the official 2017 trail brochure used as the source for trail difficulty (S0–S3 scale) and hub grouping — check it before changing difficulty/grouping for any trail whose id doesn't have a matching brochure number in its display name.
- `Material/Donnersberg/` — source GPX for the Donnersberg region (Rheinland-Pfalz, Germany — the user's home area), first sub-region "MTB Donnersberger Land". Source: https://www.mtb-donnersberger-land.de/portfolio_trail.html. 4 individual trails (Langer Stein, Hungerbrunnen, Dicke Eiche, Schlossberg). Difficulty for all 4 was given directly by the user (not sourced online) since Trailforks — linked per-trail via `url` — is bot-blocked as usual and the site itself shows no rating; cross-validated 2026-07-23 against OSM's own `mtb:scale` tags for these same trails (1↔blau, 2↔rot here — matched the user's assignment exactly). **Geometry note (2026-07-23, superseded the original GPX-based build the same day)**: the site's own GPX downloads for all 4 individual trails turned out to have placeholder `<ele>0</ele>` throughout (elevation was first backfilled via OpenTopoData `mapzen`), but more importantly the trail *shape* itself (Trailforks-exported "ridelog"/track) visibly deviated from the real trail paths rendered by this app's own OSM/OpenTopoMap base layers — the user noticed this by comparing our lines against those base-map paths directly. **OpenStreetMap has these 4 trails individually name-mapped** (`way["highway"~"path"]["name"="MTB Trail <name>"]`, findable via Overpass in the Donnersberg bounding box), and is what the 4 trails' `TRAIL_GEO` now come from (elevation still backfilled the same way via OpenTopoData per node). Match the base map, not the "best" source, if they ever diverge. See `docs/trailrunde-feature.md` for how the loop's own geometry was rebuilt to stay consistent with this.

## Running / testing changes

There is no build, lint, or test command — this is a static HTML file.

- **Must be served over local HTTP, not opened as a `file://` URL** — `python3 -m http.server` from inside `Trailmap App/`, then visit `http://localhost:8000/`. This used to only matter for the service worker/offline/tile-preload features; since region data is now fetched (see Architecture below), even the *default* region fails to load under `file://` (`boot()` detects this via `location.protocol === "file:"` and shows the `#fatalError` panel with an explanatory message instead of leaving a silently-empty map).
- No headless browser is set up **by default** in a fresh sandbox (Chromium's system deps require sudo, not available here) — but a **working, no-sudo recipe to get a real headless Chromium + Playwright running does exist, see `docs/data-sourcing-general.md`'s "Getting a real headless browser running" section** — needed for anything jsdom can't catch (see next paragraph). Check for an already-extracted `chrome_libs`/`chrome_libs_deb` dir and a Playwright chromium cache under `~/.cache/ms-playwright/` (the latter persists across sessions since it's outside the per-session scratchpad dir) before re-running the extraction from scratch.
- For automated smoke-checks of app *logic* (not layout), `jsdom` + the real `leaflet` npm package (both installable via npm without sudo) can load and execute the actual `<script>` block and let you inspect the resulting DOM — this catches real logic bugs (filtering, rendering, id/data mismatches) without needing a full browser paint. Since the app now does real `fetch()` calls for region JSON, serve it over local HTTP (see above) rather than `file://` when testing this way, and point jsdom's `url` option at that server. Two jsdom gotchas hit while building the region-loading feature, worth knowing before repeating this: (1) Node's bare `fetch` doesn't resolve relative URLs against the page location the way a browser's `window.fetch` does — resolve them yourself (`new URL(input, window.location.href)`) before delegating. (2) jsdom scopes each separately-executed `<script>` tag's top-level `const`/`let` independently — a diagnostics/test hook needs to be spliced into the *same* script block (and, since this app wraps everything in one top-level `try{...}catch(err){...}` for the fatal-error panel, at the *same block nesting depth* as the rest of the app code — e.g. right after the `boot();` call — not just anywhere after the closing `</script>`) to actually share scope with the app's variables.
- **jsdom does not implement real CSS layout** (no actual box model/flexbox/scrollbar-width computation — every element reports `0`-ish geometry) — it's only useful for logic/DOM-shape checks. Any *visual* layout bug (chip wrapping, sizing, spacing, scrollbar-driven reflow) needs the real headless Chromium from the point above instead — confirmed 2026-07-23 while diagnosing a sidebar chip-reflow bug that jsdom couldn't reproduce at all (real widths/scrollbar behavior only showed up under actual Chromium layout).
- **Deployment (since 2026-07-24)**: this directory is a git repo pushed to `https://github.com/FloMotion1980/trailmap` (public; `Paznaun App/` is deliberately excluded via `.gitignore` — it has its own separate repo). GitHub Pages serves it at `https://flomotion1980.github.io/trailmap/`, built by `.github/workflows/deploy-pages.yml`: on every push to `main` touching `Trailmap App/**`, the workflow uploads that *subfolder itself* as the Pages artifact (not the repo root — `Trailmap App/` stays a normal subfolder, no restructuring needed) via `actions/upload-pages-artifact` + `actions/deploy-pages`. Just `git push` to `main` — no manual upload step anymore. If you change `index.html` and/or `sw.js`, both are already re-deployed together automatically since the whole folder is republished as one artifact (no separate stale-cache-only-one-of-them risk at the deploy level — though the *service worker's own* cache-versioning behavior in the browser is unchanged, see `sw.js` below).
- **The Tourenbuilder has one**, though: `tools/builder_testcases.js`, pasted into the browser console with the `bikecircus` region active and builder mode on — 19 cases / 97 checks covering every junction and direction rule (each one a ride the user actually reported) plus the touch-layout list behaviour. Run it at a phone viewport. Run it after touching `builderResolve`, `junctionCandidates`, the row rendering or the drag handler. Its header lists two mutations and the failures they must produce, so you can check it still bites. See `docs/tour-builder.md`.
- Otherwise there's no automated test suite; verify changes by exercising the app in a browser (desktop and, where possible, a mobile viewport/device — a lot of the logic is mobile-specific, see below).

## Architecture of `Trailmap App/index.html`

Single HTML file, in this order: `<style>` block → HTML skeleton → one `<script>` block containing all app logic (wrapped in one top-level `try{...}catch(err){...}` that shows the `#fatalError` panel on any uncaught exception — see the jsdom gotcha above if you need to inject code at the same scope). Everything is global (no modules, no build-time imports); Leaflet is loaded from a CDN `<script>` tag.

### Region catalog + lazy-loaded per-group data (the core scaling mechanism)

Unlike the original `Paznaun App/`, trail data is **not** all embedded inline anymore — that doesn't scale as more regions get added. Instead:

- `REGION_CATALOG` — the only always-loaded, always-inline region data. `{ [groupKey]: { label, file, trailCount, bounds, subRegions: { [subKey]: {label, color} } } }`. No trail geometry lives here — `bounds` is a precomputed `[[latMin,lngMin],[latMax,lngMax]]` bounding box for flying the map to that group. `file` points at that group's JSON, e.g. `regions/paznaun.json`.
- `regions/<groupKey>.json` — one file per region group (currently `paznaun.json`, `dreilaender.json`), each shaped `{ lineTrails, trailGeo, elevationProfiles, places }` — that group's full slice of what used to be the inline `lineTrails`/`TRAIL_GEO`/`ELEVATION_PROFILES`/`PLACES`. Fetched only when the group is activated.
- `REGION_GROUPS`, `REGIONS`, `lineTrails`, `TRAIL_GEO`, `ELEVATION_PROFILES` are now **mutable, start empty**, and get populated/depopulated at runtime by two functions:
  - `activateRegionGroup(groupKey)` (async) — no-ops if already active/loading/at the `MAX_ACTIVE_REGION_GROUPS` cap; otherwise fetches `regions/<groupKey>.json`, merges everything in (`REGION_GROUPS[groupKey]`, per-catalog-sub-region `REGIONS[subKey]` entries added to `activeRegions` by default, `lineTrails.push(...)`, `Object.assign` onto `TRAIL_GEO`/`ELEVATION_PROFILES`), builds that group's Leaflet layers (`buildTrailLayer` per trail, `buildPlaceMarkers`), then persists/rerenders. All-or-nothing: a failed fetch mutates nothing.
  - `deactivateRegionGroup(groupKey)` — the exact inverse: removes that group's trails/layers/markers/sub-regions/place-markers, using `REGION_CATALOG[groupKey].subRegions` (not the mutated `REGIONS`) to know which sub-region keys belong to it, so ordering never matters.
  - Both use a stable `pendingActivation[groupKey]` guard against double-clicks/concurrent activation of the same group.
- `MAX_ACTIVE_REGION_GROUPS` (currently `3`) caps how many groups can be loaded/active simultaneously — enforced in `activateRegionGroup` and reflected in the region-picker dialog (disables not-yet-active rows once hit).
- `activeRegionGroups` (a `Set`) tracks which groups are currently loaded — separate from `activeRegions` (the finer sub-region visibility filter, unchanged from before) and `activeDiffs` (difficulty filter, unchanged).
- `lineTrails` — array of trail metadata: `{id, name, region, diff, len, up, down}`. `region` is a `REGIONS` key (sub-region), not a `REGION_GROUPS`/catalog key. **There is no `url` field** — the info panel's "Zur Tour auf der Website ↗" link and the 176 URLs behind it were removed on 2026-07-28 at the user's request, to slim the region files down. `validate_region.py` now rejects the field outright, so don't reintroduce it when building a region; GPX export stays.
- **`render()` and the sidebar chip builder (`rebuildRegionChips()`) still just iterate whatever's currently in `REGION_GROUPS`/`REGIONS`** — same dynamic-iteration pattern as before (don't hardcode a region-key list; the original Paznaun-only `render()` hardcoded `["ischgl","kappl","galtuer"]`, which is exactly the mistake this whole architecture exists to avoid repeating). The difference now is that these objects only ever contain *activated* groups, not the full catalog — the catalog (all groups, activated or not) is what the "Regionen wählen" dialog lists separately.
- **UI entry points:** a header button (`#regionsBtn`, next to the "Trailmap" title — replaced what used to be a hardcoded `<span class="sub">Paznaun · 3-Länder Enduro Trails</span>`, which wouldn't have scaled either) opens `#regionDialog`, which lists every `REGION_CATALOG` entry with an activate/deactivate toggle (this is what calls `activateRegionGroup`/`deactivateRegionGroup`). The button doubles as a live "what's active" indicator: `updateHeaderRegionsLabel()` sets its text from `Object.values(REGION_GROUPS).map(g => g.label)` — i.e. only currently-*activated* groups, never a hardcoded list — and is called every time `rebuildRegionChips()` runs (activate/deactivate/boot), so it never goes stale. The sidebar's region groups (only shown for *active* groups) each render as a `.region-group-block` — a bordered "fieldset"-style box (added 2026-07-22, the user found it visually unclear which sub-region chips belonged to which group) containing a `.region-group-row` "legend" (absolutely positioned to overlap the top border, background `var(--card-bg)` to visually cut a gap in it, exactly like an HTML `<fieldset>`/`<legend>`) and a `.region-group-chips` row with that group's sub-region chip buttons inside the box. The legend itself holds two separate elements, split 2026-07-22 after the user found the original single clickable heading confusing (one tap doing two unrelated things) and hard to hit precisely on mobile: the `.region-group-label` button (click toggles all of that group's sub-regions on/off together, and is visually filled via an `.all-active` class when every sub-region is currently active — kept in sync both on rebuild *and* whenever an individual sub-region chip is toggled, via the `syncAllActive()` closure captured per-group in `rebuildRegionChips()`, not just on a full rebuild) and a separate `.region-group-fly-btn` (📍, click flies the map to `REGION_CATALOG[groupKey].bounds`) — each with its own generously-padded touch target. On a first-ever visit (nothing in `localStorage` yet), `boot()` opens the dialog automatically after the default region loads, so the user consciously picks their region(s) instead of just landing on Paznaun unasked. A failed activation attempt shows an inline error under that region's row in the dialog (`regionActivationErrors`, keyed by group) — kept in a variable outside `renderRegionDialog()` specifically so the message survives the re-render that happens right after the attempt finishes, instead of being wiped the instant it's shown.
- **Persistence:** `activeRegionGroups`/`activeRegions`/`activeDiffs` are saved to `localStorage` (key `trailmap-active-state-v1`) after every change and restored on `boot()`. A saved group key no longer present in `REGION_CATALOG` is silently dropped (forward-compatible with catalog changes). First-ever visit (nothing saved) activates just `paznaun`.
- **Boot sequence:** `boot()` (replacing what used to be a bare top-level `render()` call) restores saved state or defaults to `["paznaun"]`, `await`s `activateRegionGroup` for each, re-applies the saved `activeRegions`/`activeDiffs` on top (since `activateRegionGroup` itself defaults everything in a freshly-loaded group to visible), then fits the map to the combined bounds of whatever ended up active. The map's hardcoded `setView([46.99,10.29],12)` (Paznaun) at init time is only the placeholder shown while `boot()`'s fetches are in flight, and the fallback if every fetch fails (e.g. first-ever visit while offline).

### Legacy note

- `TRAIL_GEO`/`ELEVATION_PROFILES` are still the names used *inside* each `regions/*.json` file's `trailGeo`/`elevationProfiles` keys and, once activated, in the live in-memory `TRAIL_GEO`/`ELEVATION_PROFILES` objects — same shapes as documented in the original `Paznaun App/` (`{ trailId: [[lat,lon],...] }` and `{ trailId: [[distanceKm,elevationM],...] }` resampled to ~100 points), just no longer inline in `index.html` or complete until their region is activated.

### How trail data gets into a region's JSON file

GPX → geometry/elevation is a well-defined pipeline, and since 2026-07-28 it is **repo-tracked in `tools/trailmap_pipeline.py`** — import it rather than writing it again. It had been re-derived from scratch in every session that added a region (~27 ad-hoc scripts in one session alone, all lost with it), which risks silent inconsistency between regions. The shape: regex point extraction (real XML parsers choke on malformed source GPX like unescaped `&` in `<name>`, or CDATA-wrapped `<ele>` values, or `lon` before `lat` in the attribute order, all of which show up across the GPX sets in `Material/`) → 0.5m point de-duplication → Douglas-Peucker with a small fixed epsilon (2m; don't simplify harder just to hit a point-count target, that visibly distorts short trails) → elevation resampled by distance (100 points, 150 above 7km, 200 above 25km) with missing/implausible values (e.g. GPS glitches reading ~0m, or the placeholder `<ele>0</ele>` in Donnersberg's downloads) interpolated. Verified against the newest region: it reproduces all 24 Dolomiti Paganella trails byte-identically. **Older regions were built to coarser parameters** (Paznaun has ~half the points and fixed 100-point profiles), so re-running the pipeline over one would change its geometry slightly — only do that when there's a reason to touch it anyway.

**After ANY change to a `regions/*.json` file, run `python tools/update_region_versions.py`.** `regions/version.json` is a md5-per-file manifest; the app fetches `regions/<key>.json?v=<hash>` and `sw.js` serves those cache-first, so that hash is the *only* thing that invalidates a cached region. A stale hash means the edit never reaches a device that already has the region, and a missing entry is worse — the URL is then unversioned and stays cached forever. Both had already happened by 2026-07-28 (an edit to `paznaun.json`, plus three regions never listed at all), which is why the validator now checks it. Also: write region files with the pipeline's own writer (one line, `separators=(", ", ": ")`) — re-dumping one with `indent=` turned a two-value change into a 24 350-line diff.

`python tools/validate_region.py [key]` checks a region against the invariants that have actually caused bugs (sub-region keys, difficulties, a leftover `url`, orphaned geometry/profiles, `trailCount`, lifts stored bottom-station-first, sub-region colours, the loop concatenation invariant, and geometry that sits implausibly far from the region centre). Run it after any region change; non-zero exit means something failed.

Metadata (name/difficulty/length/up/down) is a separate, non-automatable step — it doesn't come from the GPX, it comes from whatever official source exists for that region (tourism site scraping for Paznaun; the `BiketrailsNauders.pdf` brochure's S0–S3 scale for 3-Länder's 21 numbered trails). Where no official length/Hm exists (newer trails not in a brochure), GPX-computed length/elevation-gain-loss is an acceptable fallback — but prefer official published numbers over GPX-derived ones when both exist, to stay consistent with the rest of `lineTrails`.

**Finale Ligure specifically** has its own, more involved sourcing method (Outdooractive GPX download, route-ID extraction, difficulty-rating rules, three hard-learned lessons) — see **`docs/finale-ligure.md`**, read it before adding or correcting any Finale trail.

**Trailforks** (bot-blocked, needs a headless browser workaround) and the **general headless-Chromium-without-root setup** for this sandbox are documented in **`docs/data-sourcing-general.md`** — these apply beyond just Finale.

### Adding a new region under this model

**See `docs/adding-a-region.md` for the full runbook** — the order of operations, the decisions that need the user (difficulties where nothing official exists, the sub-region split, one region or several), and the verification step. In short:

1. Run the pipeline (`tools/trailmap_pipeline.py`) to produce that region's trail data, then shape it into `regions/<newgroup>.json` as `{ lineTrails, trailGeo, elevationProfiles, places }` — `write_region()` does the last part in the app's own formatting.
2. Add one `REGION_CATALOG` entry: `label`, `file`, `trailCount`, a computed `bounds` bounding box (`region_summary()` gives you one), and `subRegions` (label+color per sub-region/hub).
3. `python tools/validate_region.py <newgroup>`, then look at it in a browser against the base map.
4. That's it — no other code changes needed. The dialog, sidebar, `render()`, persistence, and map-fitting all already iterate the catalog/active-state dynamically.

### Map / UI conventions worth knowing before touching them

- Base layers (street/light/relief/satellite) are custom buttons, deliberately *not* Leaflet's built-in `L.control.layers` (had rendering issues in testing).
- `.leaflet-interactive:focus{ outline:none; }` suppresses the browser's default focus ring on clickable vector layers (found 2026-07-23, most noticeable clicking a Trailrunde segment) — Leaflet gives every interactive polyline/circleMarker a `tabindex`, and the native focus outline follows the path's *rectangular SVG bounding box*, not its actual shape, which for an irregular trail/loop line shows up as a stray black box-shaped "frame" rather than tracing the line itself.
- **Elevation chart is colored by the trail's own difficulty (added 2026-07-23)**: `buildElevationSvg(profile, highlight, color, trailId, reversed, segments)` takes a `color` param (`diffColor[t.diff]`, passed from `buildInfoPanelHtml`) used for both the polyline stroke and — via a new `hexToRgba(hex, alpha)` helper — the translucent area fill beneath it, for a normal trail. Previously both were hardcoded green regardless of the trail's actual difficulty, which was actively misleading since green is itself one of this app's difficulty colors (a schwarz/rot trail's chart looked like it was claiming to be easy).
  - **For a Trailrunde specifically (extended same day, per the user)**: pass `segments` instead — an array of `{distStart, distEnd, color}` mirroring the *same* per-stretch coloring already used on the map (that stretch's own trail's `diffColor`, or `CONNECTOR_COLOR` for a connector) — and the chart draws one polyline+polygon pair per segment instead of a single flat-colored one, so the profile visually matches the map exactly rather than just using the loop's own overall `diff` as one blanket color. `buildInfoPanelHtml` builds this array from `TRAIL_SEGMENTS[t.id]` (skipping any entries missing `distStart`, which only ever happens for a not-yet-backfilled loop) — when `isReversed`, each segment's `distStart`/`distEnd` is flipped (`totalDist - distEnd, totalDist - distStart`) the same way `reverseElevationProfile()` flips the profile itself, so the segment coloring and the (now-mirrored) profile line stay aligned on the x-axis.
  - `profileSlice(profile, distStart, distEnd)` (using a new `elevationAtDistance(profile, d)` interpolation helper) cuts a clean sub-range of the profile at each segment boundary — including interpolated endpoints exactly at `distStart`/`distEnd` even when those don't land on an existing profile point — so adjacent per-segment polylines meet with no visible gap or overlap.
  - The highlighted-segment `<rect>` (shown when a specific Trailrunde segment was clicked — see `docs/trailrunde-feature.md`) still works the same as before and is drawn **after** (on top of) the per-segment lines/areas now, so it reads as a "you clicked this one" tint over an already fully-colored chart, not something that gets buried underneath a segment's own fill.
- **Elevation-chart-to-map hover sync (added 2026-07-23)**: moving the mouse across a trail's (or Trailrunde's) elevation chart shows a blue dot (`var(--blau)` on the chart, `#1f5f9e`/white-stroke on the map — matching by design, not a shared constant) moving along the profile line *and* a matching dot on the map at that same point along the trail. No crosshair/guide line — tried one initially (a vertical `<line>` in the chart), removed same day per the user. Implementation: `buildElevationSvg` stamps the SVG with `data-trail-id`/`data-reversed`/`data-profile` (JSON-encoded) plus the axis-scaling constants (`data-dist-max`/`data-pad-top`/`data-pad-bottom`/`data-h`/`data-ele-min`/`data-ele-range`) needed to convert a mouse pixel position back into a distance-along-profile and then an elevation — this avoids threading extra parameters through `showTrailInfo`'s call chain, at the cost of re-deriving them from the DOM in the hover handler. One delegated `mousemove` listener on `#ipContent` (`handleEleChartHover`) handles every currently-open trail's chart generically:
    - `cumulativeDistanceKm(coords)` (new helper, using a new `haversineM` — this app previously had no client-side distance calculation at all, only in the Python build pipeline) precomputes cumulative distance per point of the trail's `TRAIL_GEO`; `getEleHoverData(svg)` caches this (plus the parsed profile) keyed by `trailId` so it's only recomputed when the hovered chart actually belongs to a *different* trail than last time, not on every mousemove pixel.
    - `latLngAtDistance(coords, cumDist, targetKm, reversed)` binary-searches `cumDist` and linearly interpolates between the two bracketing points — `reversed` measures from the *end* of `coords` instead of the start, since (per the "Reverse direction" feature further below) the coords array itself is never physically reordered, only which end counts as "start" for markers/numbers.
    - A single reusable `eleHoverMapMarker` (`L.circleMarker`, `interactive:false`) is added to the map on first hover and repositioned via `setLatLng` on every subsequent move rather than recreated — removed again on `mouseleave` from `#ipContent` or when the mouse moves off the `.ele-chart` onto some other part of the same panel.
    - Works generically for a Trailrunde too — `data-trail-id` is just whatever `t.id` `buildInfoPanelHtml` was called with, and a loop's `TRAIL_GEO[loopId]` is already the full concatenated track, so the hover dot walks the *entire* loop, not just one segment.
- Difficulty color scheme is ski-slope style: green/blue/red/black (`gruen`/`blau`/`rot`/`schwarz`).
- **A trail's map label carries its difficulty as a coloured dot before the name** (`trailLabelHtml()`, `.tl-diff`), mirroring the 🚡 that starts a lift's label — the user's own analogy (2026-07-28). Applies to all three places a trail name becomes a tooltip: `hitLine`'s own label, a loop segment's hover label, and a segment's permanent `applyNameLabels` label. Worth knowing why it is needed at all: the label is the one place the map named a trail without saying how hard it is, and the label often covers the very line whose colour would have told you.
- **The sidebar has its own scroll-to-top button** (`#sidebarTopBtn`), shown once `aside.scrollTop > 180`. The header title still does the same job, but on a phone the sidebar is `position:fixed; top:0; z-index:2500` and **covers the header entirely**, so the title is unreachable exactly when a long list needs it (measured, 2026-07-28). It is `position:sticky` as the `aside`'s last child rather than fixed, so it positions itself against whichever width the sidebar has (350px column vs. `min(88vw,340px)` drawer) with no hardcoded geometry. Note a floating button like this was *rejected* in 2026-07-24 in favour of the title; the phone case is what reversed that.
- **A region group's 📍 fly button sits in the top-right corner of its `.region-group-block`**, not in the legend row (moved 2026-07-28). In the legend it shared a flex line with a label whose width varies with the region name and its trail count, so it never had a predictable position. Same `translateY(-50%)` and `--card-bg` background as the legend, so it straddles the border and cuts its own gap in it.
- **Place labels (village names) have their own "Orte" switch** in Kartenoptionen (`showPlaces`, default on, persisted). One global on/off — a `places` entry carries no sub-region, it belongs to a whole region group, so there is nothing finer to filter on. `applyPlaceVisibility()` is called by the toggle *and* at the end of `activateRegionGroup`, so a group activated while the switch is off doesn't light its labels up.
- **A Trailrunde's connector stretches are drawn at `CONNECTOR_WEIGHT` (2.8), thinner than a trail's `BASE_WEIGHT` (3.5)** — they are the least important part of a loop. Because of that, restoring a line's width can no longer be one flat `setStyle` on the group: a segmented loop's `styleTarget` is a `featureGroup` containing those connectors, so a group-wide `BASE_WEIGHT` would silently fatten them on the first hover *anywhere* on the map. Each layer therefore carries `_tmBaseWeight` and `applyLineWeight()` restores per-layer widths, adding the same hover delta to whatever the baseline is. A loop with *no* `trailSegments` is a different case and stays at `BASE_WEIGHT`: there the whole route is dashed grey, not a connector.
- Each trail line has a thin visible polyline plus a separate, much wider invisible polyline on top for touch hit-testing.
- Selection highlight is a separate yellow polyline drawn *behind* the colored line (not a recolor), sized wider than the max hover width.
- The info panel for a selected trail is a custom floating `<div>` (`#infoPanel`), not a Leaflet popup — positioned differently for desktop / mobile portrait / mobile landscape / standalone-PWA mode.
- "Solo mode" dims all other trails to ~15% opacity (not hidden) and hides their name tooltips. `resetAllHoverStyles()` and `setHover()`'s hover-off path both need to restore each trail's *baseline* opacity via `baselineLineOpacity(lid)` (0.85 normally, but 0.15/0.9 while solo mode is active) rather than hardcoding 0.85 — hardcoding it was a real bug: just moving the mouse over any other trail while solo mode was active silently cancelled the dimming (no click needed, since hover fires `resetAllHoverStyles` on every other layer).
- Reliable mobile/orientation detection is done in JS (`window.innerWidth/innerHeight`, `navigator.standalone`) toggling a class on `<html>`, *not* via CSS media queries alone — media queries were found unreliable for this on real devices (see summary doc §6 for the specifics that were tried and rejected).
- **The tracking pill (`#liveStatus`) is a live readout, not a label** (2026-07-29): `±<accuracy> m · <fix age> · 🧭 <heading>° · <fixes>/<pans>`. It exists because two field reports could not be diagnosed from the code — the map not scrolling while the dot kept updating, and the heading cone freezing during a lift ride — and both are *silent* failures, so nothing was logged. The parts each answer one question: the **fix age ticks on its own timer**, so "GPS stopped" is distinguishable from "GPS fine, map at fault"; `🧭 —` means no compass reading ever arrived (permission), while `🧭 242°!` means readings arrived and then stopped (magnetic interference — a steel gondola is the suspected cause of the frozen cone); and **fixes vs. pans** localises a non-following map to either the follow branch not being reached or Leaflet swallowing the pan. The pill turns rust past `STALE_FIX_MS`. Kept permanently rather than as a debug toggle: accuracy is honest information when the dot sits 30 m off the trail in the woods. On touch layouts it sits *below* the top button row — centred on the viewport it drifted into the Trails button, whose free space is not symmetric with the locate button's.
- **The compass permission MUST be requested from a `click`/`touchend` handler, never only from `pointerdown`.** Safari grants the user activation that `DeviceOrientationEvent.requestPermission()` requires on click, not on pointerdown — moving the call to pointerdown (2026-07-29, to escape the hold gesture's `setTimeout`, which is genuinely not an activation) made the request reject outright and killed the heading cone for a whole day. It is now asked from both, each guarded on `orientationHandler === null`, so whichever the platform honours wins. The readout tells the two apart: `✕R` = rejected (our bug, no valid activation), `✕D` = the OS or user refused (iPhone: Einstellungen → Safari → Bewegung & Ausrichtung), `✕!` = no `DeviceOrientationEvent`, `E7` = 7 events arrived carrying no usable heading (calibration/interference, *not* permission).
- **Kartenoptionen ends with the running build's version** (`#appVersion`), read from the live service-worker cache name and the worker's state — deliberately not from a constant, which would only report what the source says. Three debugging rounds were spent on "still broken" reports that turned out to be a cached build, because an iOS home-screen PWA keeps its old worker until the app is fully killed; the line says "Update wartet — App schließen und neu öffnen" when a newer worker is installed but not in control. Check it before diagnosing any "the fix didn't work" report.
- Live location uses the device compass (`DeviceOrientationEvent`, `webkitCompassHeading` on iOS) rather than GPS course, with manual angle smoothing that tracks an *unbounded* display angle separately from the normalized 0–360° heading (needed to avoid the CSS transition "spinning the wrong way" across the 0°/360° wrap).
- "Follow me" mode uses `watchPosition` + `panTo` per update (not `flyTo`, which would fight the user's zoom), with `flyTo` only on the very first fix.
- Region filter chips and trail-list groups both render two levels (`region-group-label`/`region-group-title` for the `REGION_GROUPS` tier, `hub-title` for the `REGIONS` tier) — a group heading is only shown if at least one of its sub-regions has a visible trail under the current filters, same rule applied one level down for sub-region headings.
- **Trail-card sub-region tinting**: each `.trail-card` in the sidebar list gets a light background tint of its sub-region's own `color` (added 2026-07-22 per the user's idea, for at-a-glance scannability of which sub-region a trail belongs to) — computed live via CSS `color-mix(in srgb, ${color} 16%, white)`, set as an inline `--card-tint` custom property in `render()` (not a literal `background-color`, specifically so the existing `.trail-card:hover`/`.trail-card.selected` class rules — both more specific than the plain `.trail-card{background:var(--card-tint,transparent)}` base rule — keep overriding correctly on hover/selection, same as before this was added). Deliberately reuses each sub-region's *existing* saturated `color` value (already used for its chip) rather than maintaining a second, hand-picked pastel palette — no data-model change needed, and it stays in sync automatically if a sub-region's color is ever changed. Colors only need to be distinct **within one region group** (the user confirmed 2026-07-22 that repeats *across* different groups are fine, and expected as more regions get added over time) — when adding a new sub-region, only check its color against its own group's siblings, not the whole catalog. The one cross-cutting exception: a sub-region's color still shouldn't equal the group-label button's fixed `--forest` color, since that button sits directly above its own group's sub-region chips in the same bordered box (this bit the Paznaun "Ischgl/Samnaun" entry, since fixed 2026-07-22). Colors are authored once, statically, per sub-region in `REGION_CATALOG` — not computed/assigned at runtime based on which groups happen to be active simultaneously.
- **Trail category filters**: every trail falls into exactly one of three mutually-exclusive display categories — `loop` (Trailrunde), `uphill` (EMTB uphill), or otherwise "regular"/Downhill — each independently toggleable via its own sidebar switch (`showLoopToggle`/`showUphillToggle`/`showDownhillToggle`, all default-on, persisted like `activeDiffs`). `render()`'s visibility check picks exactly one of the three toggle states per trail (`t.loop ? showLoop : (t.uphill ? showUphill : showDownhill)`) rather than ANDing multiple independent booleans, since a trail can't be in more than one category — this lets a user isolate e.g. only uphill + loop trails by turning Downhill off, which is the point (added 2026-07-22 per the user's request).
- The map's initial `setView([46.99, 10.29], 12)` (Paznaun) is just the pre-`boot()` placeholder view — see the boot sequence above for how the real initial view (fit to whatever regions actually end up active) is computed.
- **Sidebar filter panel (collapsible sections, visible-trail counts, current-region indicator)** — see **`docs/sidebar-filters-ui.md`** for the full design (which control lives in which section and why, two CSS-inheritance regressions found/fixed, the count/current-region implementation details).
- **EMTB uphill trails**: an optional `uphill: true` field on a `lineTrails` entry marks a trail as an e-bike uphill route (seen first in Finale Ligure's Le Manie hub, e.g. "Radici") — deliberately *not* folded into `diff`, since uphill/downhill is a different axis than difficulty and such trails can often be ridden either direction. Shows as a ⚡ badge (`.badge-uphill`) in both the trail-list card and the info panel `<h3>`. `showUphill` (persisted like `activeDiffs`) is a single global on/off toggle (sidebar checkbox, not a per-difficulty chip set) that hides/shows all uphill-flagged trails regardless of region/difficulty filters.
- **`#locateBtn` (the map's own "my location" button) sits top right on every layout, and is touch-only** (`display:none` in the base rule, `display:flex` only in the `(max-width:768px),(pointer:coarse)` block). It was bottom right until 2026-07-28, moving to the top only while the Tourenbuilder sheet was open; the user asked for that position permanently, which collapsed four positioning rules into one and removed an `!important`. Don't reintroduce a per-mode position — the corner is free on every layout (drawer toggle top left, `#liveStatus` top centre, and in `landscape-compact` the button ends at y=117 while `#infoPanel` starts at y=125).
- **Locate button**: the info panel's 📍 `.locate-btn` (added 2026-07-23) flies the map to that trail's own `layer.bounds`, same `flyToTrailBounds()` used for the sidebar card click and the region-group fly button — useful once the map has drifted away from the currently-open trail (e.g. after exploring a Trailrunde's segments, or just panning around) without needing to close and reopen the panel. Sits inline in the `<h3>` next to the trail name/badges (per the user's preference) rather than alongside the solo/reverse buttons in `.ip-trail` — smaller (18px vs. those buttons' 22px) to fit the heading's line height.
- **Reverse direction**: the info panel's 🔄 button is available on *every* trail (not just uphill ones — generalized 2026-07-22 per the user pointing out the uphill-only version was pointless, since it only mirrored the elevation profile/numbers without actually letting you view the trail ridden backwards). Toggles a per-open-panel `reversedId` state (mirrors the existing `soloId` pattern, including the "reset when a different trail opens" rule, which now also calls `applyReversedEndpoints` on the *previously*-reversed trail to put its markers back before switching). Swaps the displayed up/down numbers and mirrors the elevation profile via `reverseElevationProfile()`, **and** now also actually swaps the map's `startDot`/`startMarker`/`endMarker` positions between the two ends of `layer.coords` via `applyReversedEndpoints(id)` — the marker objects keep their own identity/color/tooltip ("Start" stays green, "Ziel" stays red), only their `setLatLng` position changes, so a reversed trail visually shows you riding it the other way, not just different numbers next to the same polyline. Works the same for loop trails (`TRAIL_SEGMENTS` doesn't encode a direction, so segment coloring is unaffected by reversing).
- **List auto-scroll on map selection**: `selectTrail(id, card)` calls `card.scrollIntoView({behavior:"smooth", block:"nearest"})` whenever a card is selected (added 2026-07-22) — matters when the selection came from clicking a trail *on the map* rather than in the list, since the card could be scrolled off-screen in a completely different region/hub group.
- **Tourenbuilder**: a sidebar mode (`builderMode`) for assembling a route by clicking trails and lifts in ride order — reorder, flip direction, remove, see the chain highlighted and the running totals, and export the ordered element list. Exists because deriving a Tour from a recorded GPX is inherently a guessing game (the Challenge tours needed three rounds of threshold tuning and still had real errors); stating the route is not. **First cut on purpose: gaps between elements are left visible and the export deliberately omits `distStart`/`distEnd` and the elevation profile**, both of which would be fabrications until the gaps are closed. **See `docs/tour-builder.md`** — note especially that every click site funnels through one `builderTryAdd()` guard (9 of them) and that the highlight has its own pane below the trails.
- **Bike lifts**: an optional `lifts` array per `regions/<group>.json` adds mountain lifts that actually carry bikes in summer as their own map object type (deliberately *not* entries in `lineTrails` with a flag — a lift has no difficulty and must stay out of the trail counters/list/profiles). Drawn OSM-style as a thin line with dots whose spacing stays constant on screen at any zoom (which falls out of SVG `stroke-dasharray` being screen-space — no zoom handler needed), toggled by one sidebar switch (`showLifts`), clickable for a sparse info panel. `TRAIL_SEGMENTS` entries may carry `liftId` instead of `trailId`, so a Tour's gondola stretch reads as a lift ride rather than an anonymous connector. **Whether a lift belongs in the data comes from the operator's own summer-lift page, never OSM's `aerialway:bicycle` tag** — that tag was wrong in both directions in Saalbach. **See `docs/lifts-feature.md`** for the full design, the operator-vs-OSM sourcing rule, the connector-splitting method, and two invariants (plus an ordering bug) worth knowing before touching this code.
- **Trailrunden (multi-trail loop routes)**: an optional `loop: true` field on a `lineTrails` entry marks it as a route combining several of a region's individual trails plus connecting fireroad/access stretches (first example: Donnersberg's "Wasser & Holz"). Shows a 🔁 badge next to the name. Data model: `TRAIL_GEO[id]` still holds the loop's full flat coordinate list as normal — the loop-specific part is a parallel, optional `TRAIL_SEGMENTS[id]` entry (`[{coords, trailId|null}, ...]`) marking which stretches are which component trail vs. a connector. **See `docs/trailrunde-feature.md` for the full design** — geometry-reuse rules, the critical `TRAIL_GEO`/`TRAIL_SEGMENTS` consistency invariant, per-segment click/hover/name-labels, elevation-chart segment coloring + map hover-sync, and a Leaflet z-order bug + a tooltip-stuck-open bug both worth knowing before touching this code.

### Service worker (`sw.js`)

- App shell (`index.html`) is network-first with cache fallback (so updates land while online, offline still works).
- Everything else (Leaflet assets, map tiles) is cache-first, filled in the background.
- Any cache write inside a fetch handler must be wrapped in `event.waitUntil(...)` — without it the browser can kill the service worker before the write completes, silently dropping tiles from the cache (this was a real, previously-fixed bug).
- Tile fetches must use `{mode:'no-cors'}` — public tile servers don't send CORS headers, so a plain same-origin-mode `fetch()` fails silently.
- `sw.js`'s fetch handler itself is generic and needs no changes to support a new region — its cache-first branch already covers `fetch("regions/<groupKey>.json")` the same way it covers CDN Leaflet assets. `APP_SHELL` (precached at install time) intentionally includes only the *default* region (`regions/paznaun.json`), so a first-ever visit works fully offline without precaching every region — that would defeat the point of lazy loading. `CACHE_NAME` in `sw.js` must match `PRELOAD_CACHE_NAME` in `index.html`.
- **`style.css` is cache-first and versioned in its URL.** Three things must stay in sync on every CSS change: the `?v=` in the `<link rel="stylesheet">` in `index.html`, `STYLE_URL` in `sw.js`, and (since the stylesheet is in `APP_SHELL`) a `CACHE_NAME`/`PRELOAD_CACHE_NAME` bump. The version in the URL is what actually makes a change arrive — `index.html` is network-first, so a new deploy asks for a stylesheet URL the old cache cannot answer. Do **not** switch the stylesheet to network-first instead (tried 2026-07-27, rejected by the user): this app is used offline and on one bar of signal, where that stalls the whole page behind a request timeout. Why it matters more than it looks: if a new `index.html` is paired with an old `style.css`, a newly added element has *no rules at all*, therefore no `position:absolute`, and paints behind `#map` (`position:absolute; inset:0`) — it does not look unstyled, it disappears completely. That is exactly how the pinned Tourenbuilder sheet went missing on the user's phone while everything else looked normal.
