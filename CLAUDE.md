## Running / testing changes

There is no build, lint, or test command — this is a static HTML file.

- **Must be served over local HTTP, not opened as a `file://` URL** — `python3 -m http.server` from inside `Trailmap App/`, then visit `http://localhost:8000/`. This used to only matter for the service worker/offline/tile-preload features; since region data is now fetched (see Architecture below), even the *default* region fails to load under `file://` (`boot()` detects this via `location.protocol === "file:"` and shows the `#fatalError` panel with an explanatory message instead of leaving a silently-empty map).
- No headless browser is set up **by default** in a fresh sandbox (Chromium's system deps require sudo, not available here) — but a **working, no-sudo recipe to get a real headless Chromium + Playwright running does exist, see `docs/data-sourcing-general.md`'s "Getting a real headless browser running" section** — needed for anything jsdom can't catch (see next paragraph). Check for an already-extracted `chrome_libs`/`chrome_libs_deb` dir and a Playwright chromium cache under `~/.cache/ms-playwright/` (the latter persists across sessions since it's outside the per-session scratchpad dir) before re-running the extraction from scratch.
- For automated smoke-checks of app *logic* (not layout), `jsdom` + the real `leaflet` npm package (both installable via npm without sudo) can load and execute the actual `<script>` block and let you inspect the resulting DOM — this catches real logic bugs (filtering, rendering, id/data mismatches) without needing a full browser paint. Since the app now does real `fetch()` calls for region JSON, serve it over local HTTP (see above) rather than `file://` when testing this way, and point jsdom's `url` option at that server. Two jsdom gotchas hit while building the region-loading feature, worth knowing before repeating this: (1) Node's bare `fetch` doesn't resolve relative URLs against the page location the way a browser's `window.fetch` does — resolve them yourself (`new URL(input, window.location.href)`) before delegating. (2) jsdom scopes each separately-executed `<script>` tag's top-level `const`/`let` independently — a diagnostics/test hook needs to be spliced into the *same* script block (and, since this app wraps everything in one top-level `try{...}catch(err){...}` for the fatal-error panel, at the *same block nesting depth* as the rest of the app code — e.g. right after the `boot();` call — not just anywhere after the closing `</script>`) to actually share scope with the app's variables.
- **jsdom does not implement real CSS layout** (no actual box model/flexbox/scrollbar-width computation — every element reports `0`-ish geometry) — it's only useful for logic/DOM-shape checks. Any *visual* layout bug (chip wrapping, sizing, spacing, scrollbar-driven reflow) needs the real headless Chromium from the point above instead — confirmed 2026-07-23 while diagnosing a sidebar chip-reflow bug that jsdom couldn't reproduce at all (real widths/scrollbar behavior only showed up under actual Chromium layout).
- **Deployment (since 2026-07-24)**: this directory is a git repo pushed to `https://github.com/FloMotion1980/trailmap` (public; `Paznaun App/` is deliberately excluded via `.gitignore` — it has its own separate repo). GitHub Pages serves it at `https://flomotion1980.github.io/trailmap/`, built by `.github/workflows/deploy-pages.yml`: on every push to `main` touching `Trailmap App/**`, the workflow uploads that *subfolder itself* as the Pages artifact (not the repo root — `Trailmap App/` stays a normal subfolder, no restructuring needed) via `actions/upload-pages-artifact` + `actions/deploy-pages`. Just `git push` to `main` — no manual upload step anymore. **Because the whole subfolder is the artifact, everything in `Trailmap App/` is published publicly and reachable by URL — so only the app's own files belong there.** One-off editors, review pages and debug artifacts go in `tools/` (that is why `tools/donnersberg-candidates-review.html`, a self-contained 1 MB Donnersberg trail editor, was moved out of the app folder on 2026-07-30). If you change `index.html` and/or `sw.js`, both are already re-deployed together automatically since the whole folder is republished as one artifact (no separate stale-cache-only-one-of-them risk at the deploy level — though the *service worker's own* cache-versioning behavior in the browser is unchanged, see `sw.js` below).
- **There IS a test library, in `tests/` — read `tests/README.md` before adding to it.** One entry point: `python tests/run.py --changed` runs the Python suites and bundles the affected browser suites into one paste-ready file. Fifteen suites, 178 cases, 771 checks (all green as of 2026-08-05). **Keep the browser window visible while a browser suite runs** — a hidden tab throttles its timers to ~1/minute and the run never finishes; visible it takes ~25 s. Three things about it are non-obvious and will cost you an hour each if you rediscover them: (1) **serve the repo root, not `Trailmap App/`** — a suite loaded cross-origin reports every error as an opaque `Script error.` and the app's `window.onerror` turns that into its fatal panel; (2) **which tests to run is declared in the suite headers** (`@files`/`@touches`/`@always`), not in any doc, and a changed file no suite claims is reported as a `GAP`; (3) **`async function boot()` and `activateRegionGroup()` are NOT callable** from a suite — Annex B block-hoisting covers plain function declarations only, so those go through the UI or through `TM.bootFresh()`, which boots a second copy in an off-screen same-origin iframe. Every suite starts from `TM.baseline()` (order-dependence caused the first false failure) and waits by polling, never sleeping (Leaflet fades tooltips out and animates the map for 0.6 s). `tests/MUTATIONS.md` records what has actually been verified and what has not.
- **The Tourenbuilder's suite is `tests/browser/builder.js`** (moved there from `tools/` on 2026-07-31): 19 cases / 97 checks covering every junction and direction rule (each one a ride the user actually reported) plus the touch-layout list behaviour. It is `@standalone` — it brings its own harness, so paste it alone, with the `bikecircus` region active, builder mode on, at a phone viewport. Run it after touching `builderResolve`, `junctionCandidates`, the row rendering or the drag handler. See `docs/tour-builder.md`.
- **The lift/solo/label/count/boot cases live in `tests/browser/` now** (split out of the former `tools/lift_testcases.js` on 2026-07-31, one suite per functional area: `solo`, `labels`, `filters`, `lists`, `lifts`, `regions`). Run them after touching `applySolo`/`clearSolo`, `applyLiftVisibility`, `applyLiftSegmentOpacity`, `liftPassesFilters`, `applyNameLabels`, `setLabelHovered`, the lists, the summary counts, or anything in `boot()` — or just let `python tests/run.py --changed` decide. Two techniques in them are worth reusing: they read the **map's own SVG** (pane plus stroke colour/width tells a standalone lift from a Tour's own lift stretch) rather than app state, and they get a genuine first-painted frame from an **off-screen same-origin iframe**.
- **Standing rule (user, 2026-07-31): whenever logic can be tested, test it** — extend one of the two suites in the same commit as the change, so the next change can't silently undo it. Both suites are validated by mutation, and their headers record which mutations produce which failures; keep that up to date, since a suite nobody has watched fail proves nothing. Writing the test is also how the `boot().catch` gap was found: mutation-testing showed that a throw in the async half of `boot()` produced a silent half-started app.
- Beyond those two suites there is no automated test runner; verify changes by exercising the app in a browser (desktop and, where possible, a mobile viewport/device — a lot of the logic is mobile-specific, see below).

## Architecture of `Trailmap App/index.html`

Single HTML file, in this order: `<style>` block → HTML skeleton → one `<script>` block containing all app logic (wrapped in one top-level `try{...}catch(err){...}` that shows the `#fatalError` panel on any uncaught exception — see the jsdom gotcha above if you need to inject code at the same scope). Everything is global (no modules, no build-time imports); Leaflet is loaded from a CDN `<script>` tag.

**The `#fatalError` panel's own copy must stay generic** (fixed 2026-08-04, user: "Diese iPhone Tipp solltest du aus der Fehlermeldung entfernen. Er stimmt nicht"). It used to carry two paragraphs written for the era when this was a file opened out of the Files app — "meistens scheitert das, wenn eine Datei nur als Vorschau geöffnet wird" plus an iPhone-specific "In Safari öffnen" tip — neither of which is true of an installed PWA served over HTTPS. The one case those paragraphs actually described, a genuine `file://` load, already writes its own specific message into `#fatalErrorMsg` from `boot()` (see above), so the static markup needs nothing case-specific either: it now just says reload, then close-and-reopen if reloading doesn't help (the usual cause once a fresh service worker is installed but not yet in control — see the version line in Kartenoptionen).

### Region catalog + lazy-loaded per-group data (the core scaling mechanism)

Unlike the original `Paznaun App/`, trail data is **not** all embedded inline anymore — that doesn't scale as more regions get added. Instead:

- `REGION_CATALOG` — the only always-loaded, always-inline region data. `{ [groupKey]: { label, file, trailCount, bounds, subRegions: { [subKey]: {label, color} } } }`. No trail geometry lives here — `bounds` is a precomputed `[[latMin,lngMin],[latMax,lngMax]]` bounding box for flying the map to that group. `file` points at that group's JSON, e.g. `regions/paznaun.json`.
- `regions/<groupKey>.json` — one file per region group (currently `paznaun.json`, `dreilaender.json`), each shaped `{ lineTrails, trailGeo, elevationProfiles, places }` — that group's full slice of what used to be the inline `lineTrails`/`TRAIL_GEO`/`ELEVATION_PROFILES`/`PLACES`. Fetched only when the group is activated.
- `REGION_GROUPS`, `REGIONS`, `lineTrails`, `TRAIL_GEO`, `ELEVATION_PROFILES` are now **mutable, start empty**, and get populated/depopulated at runtime by two functions:
  - `activateRegionGroup(groupKey)` (async) — no-ops if already active/loading/at the `MAX_ACTIVE_REGION_GROUPS` cap; otherwise fetches `regions/<groupKey>.json`, merges everything in (`REGION_GROUPS[groupKey]`, per-catalog-sub-region `REGIONS[subKey]` entries added to `activeRegions` by default, `lineTrails.push(...)`, `Object.assign` onto `TRAIL_GEO`/`ELEVATION_PROFILES`), builds that group's Leaflet layers (`buildTrailLayer` per trail, `buildPlaceMarkers`), then persists/rerenders. All-or-nothing: a failed fetch mutates nothing.
  - `deactivateRegionGroup(groupKey)` — the exact inverse: removes that group's trails/layers/markers/sub-regions/place-markers, using `REGION_CATALOG[groupKey].subRegions` (not the mutated `REGIONS`) to know which sub-region keys belong to it, so ordering never matters.
  - Both use a stable `pendingActivation[groupKey]` guard against double-clicks/concurrent activation of the same group.
- `MAX_ACTIVE_REGION_GROUPS` (currently `3`) caps how many groups can be loaded/active simultaneously — enforced in `activateRegionGroup` and reflected in the region-picker dialog (disables not-yet-active rows once hit).
- `activeRegionGroups` (a `Set`) tracks which groups are currently loaded — separate from `activeRegions` (the finer sub-region visibility filter, unchanged from before) and `activeDiffs` (difficulty filter, unchanged).
- `lineTrails` — array of trail metadata: `{id, name, region, diff, len, up, down}`. `region` is a `REGIONS` key (sub-region), not a `REGION_GROUPS`/catalog key. **There is no `url` field** — the info panel's "Zur Tour auf der Website ↗" link and the 176 URLs behind it were removed on 2026-07-28 at the user's request, to slim the region files down. `validate_region.py` now rejects the field outright, so don't reintroduce it when building a region; GPX export stays.
- **`render()` and the sidebar chip builder (`rebuildRegionChips()`) still just iterate whatever's currently in `REGION_GROUPS`/`REGIONS`** — same dynamic-iteration pattern as before (don't hardcode a region-key list; the original Paznaun-only `render()` hardcoded `["ischgl","kappl","galtuer"]`, which is exactly the mistake this whole architecture exists to avoid repeating). The difference now is that these objects only ever contain *activated* groups, not the full catalog — the catalog (all groups, activated or not) is what the "Regionen wählen" dialog lists separately.
- **UI entry points:** a header button (`#regionsBtn`, next to the "Trailmap" title — replaced what used to be a hardcoded `<span class="sub">Paznaun · 3-Länder Enduro Trails</span>`, which wouldn't have scaled either) opens `#regionDialog`, which lists every `REGION_CATALOG` entry with an activate/deactivate toggle (this is what calls `activateRegionGroup`/`deactivateRegionGroup`). The button doubles as a live "what's active" indicator: `updateHeaderRegionsLabel()` sets its text from `Object.values(REGION_GROUPS).map(g => g.label)` — i.e. only currently-*activated* groups, never a hardcoded list — and is called every time `rebuildRegionChips()` runs (activate/deactivate/boot), so it never goes stale. The sidebar's region groups (only shown for *active* groups) each render as a `.region-group-block` — a bordered "fieldset"-style box (added 2026-07-22, the user found it visually unclear which sub-region chips belonged to which group) containing a `.region-group-row` "legend" (absolutely positioned to overlap the top border, background `var(--card-bg)` to visually cut a gap in it, exactly like an HTML `<fieldset>`/`<legend>`) and a `.region-group-chips` row with that group's sub-region chip buttons inside the box. The legend itself holds two separate elements, split 2026-07-22 after the user found the original single clickable heading confusing (one tap doing two unrelated things) and hard to hit precisely on mobile: the `.region-group-label` button (click toggles all of that group's sub-regions on/off together, and is visually filled via an `.all-active` class when every sub-region is currently active — kept in sync both on rebuild *and* whenever an individual sub-region chip is toggled, via the `syncAllActive()` closure captured per-group in `rebuildRegionChips()`, not just on a full rebuild) and a separate `.region-group-fly-btn` (📍, click flies the map to `REGION_CATALOG[groupKey].bounds`) — each with its own generously-padded touch target. On a first-ever visit (nothing in `localStorage` yet), `boot()` opens the dialog automatically after the default region loads, so the user consciously picks their region(s) instead of just landing on Paznaun unasked. A failed activation attempt shows an inline error under that region's row in the dialog (`regionActivationErrors`, keyed by group) — kept in a variable outside `renderRegionDialog()` specifically so the message survives the re-render that happens right after the attempt finishes, instead of being wiped the instant it's shown.
- **Persistence:** `activeRegionGroups`/`activeRegions`/`activeDiffs` are saved to `localStorage` (key `trailmap-active-state-v1`) after every change and restored on `boot()`. A saved group key no longer present in `REGION_CATALOG` is silently dropped (forward-compatible with catalog changes). A saved state **missing** `activeRegions`/`activeDiffs` entirely — from an older build, hand-edited, or truncated — no longer crashes `boot()`: it used to read `saved.activeRegions.filter(...)` and `new Set(saved.activeDiffs)` unguarded, and a missing key threw `Cannot read properties of undefined (reading 'filter')`, putting up the fatal panel on **every** load, which on a home-screen PWA is not something a rider can dismiss or clear themselves (found 2026-08-04). The fix is in two places and both matter: `restoreActiveState()` deletes either key outright if it is not an array (rather than inventing a value for it), and `boot()` only overwrites `activeDiffs`/`activeRegions` when the saved value **is** an array — otherwise it leaves whichever default was already in place (the four difficulties; every sub-region of a freshly-activated group, which `activateRegionGroup()` already marks visible). The first version of this fix defaulted a missing key to `[]` directly, which is NOT the same thing: an empty array is a real, deliberate "nothing visible" and boot() must keep respecting it, while a missing key means "never set" and should leave the existing default alone — conflating the two silently hid every trail in the freshly-loaded region instead of crashing, which a test caught. No first-ever-visit default region any more (2026-08-04, user, after noticing "Silvretta Bike Arena" -- Paznaun's own catalog label -- already marked Aktiv in the dialog on a session that had never chosen anything: "Das sollte nicht sein"). `boot()`'s `initialGroups` is `saved ? saved.activeRegionGroups : []` — no `["paznaun"]` fallback on either side of that ternary. This also fixes the same mistake one level down for a RETURNING visitor: `saved.activeRegionGroups.length` being falsy used to silently re-activate Paznaun even when the empty array was itself a deliberate choice (every region deactivated on purpose). An empty `initialGroups` degrades cleanly — the bounds-fit later in `boot()` already guards on `combinedBounds.isValid()`, and the header/section already read "Regionen wählen" with nothing active.
- **Boot sequence:** `boot()` (replacing what used to be a bare top-level `render()` call) restores saved state or defaults to `["paznaun"]`, `await`s `activateRegionGroup` for each, re-applies the saved `activeRegions`/`activeDiffs` on top (since `activateRegionGroup` itself defaults everything in a freshly-loaded group to visible), then fits the map to the combined bounds of whatever ended up active. The map's hardcoded `setView([46.99,10.29],12)` (Paznaun) at init time is only the placeholder shown while `boot()`'s fetches are in flight, and the fallback if every fetch fails (e.g. first-ever visit while offline).

### Legacy note

- `TRAIL_GEO`/`ELEVATION_PROFILES` are still the names used *inside* each `regions/*.json` file's `trailGeo`/`elevationProfiles` keys and, once activated, in the live in-memory `TRAIL_GEO`/`ELEVATION_PROFILES` objects — same shapes as documented in the original `Paznaun App/` (`{ trailId: [[lat,lon],...] }` and `{ trailId: [[distanceKm,elevationM],...] }` resampled to ~100 points), just no longer inline in `index.html` or complete until their region is activated.

### How trail data gets into a region's JSON file

GPX → geometry/elevation is a well-defined pipeline, and since 2026-07-28 it is **repo-tracked in `tools/trailmap_pipeline.py`** — import it rather than writing it again. It had been re-derived from scratch in every session that added a region (~27 ad-hoc scripts in one session alone, all lost with it), which risks silent inconsistency between regions. The shape: regex point extraction (real XML parsers choke on malformed source GPX like unescaped `&` in `<name>`, or CDATA-wrapped `<ele>` values, or `lon` before `lat` in the attribute order, all of which show up across the GPX sets in `Material/`) → 0.5m point de-duplication → Douglas-Peucker with a small fixed epsilon (2m; don't simplify harder just to hit a point-count target, that visibly distorts short trails) → elevation resampled by distance (100 points, 150 above 7km, 200 above 25km) with missing/implausible values (e.g. GPS glitches reading ~0m, or the placeholder `<ele>0</ele>` in Donnersberg's downloads) interpolated. Verified against the newest region: it reproduces all 24 Dolomiti Paganella trails byte-identically. **Older regions were built to coarser parameters** (Paznaun has ~half the points and fixed 100-point profiles), so re-running the pipeline over one would change its geometry slightly — only do that when there's a reason to touch it anyway.

**After ANY change to a `regions/*.json` file, run `python tools/update_region_versions.py`.** `regions/version.json` is a md5-per-file manifest; the app fetches `regions/<key>.json?v=<hash>` and `sw.js` serves those cache-first, so that hash is the *only* thing that invalidates a cached region. A stale hash means the edit never reaches a device that already has the region, and a missing entry is worse — the URL is then unversioned and stays cached forever. Both had already happened by 2026-07-28 (an edit to `paznaun.json`, plus three regions never listed at all), which is why the validator now checks it. Also: write region files with the pipeline's own writer (one line, `separators=(", ", ": ")`) — re-dumping one with `indent=` turned a two-value change into a 24 350-line diff.

`python tools/validate_region.py [key]` checks a region against the invariants that have actually caused bugs (sub-region keys, difficulties, a leftover `url`, orphaned geometry/profiles, `trailCount`, lifts stored bottom-station-first, sub-region colours, the loop concatenation invariant, and geometry that sits implausibly far from the region centre). Run it after any region change; non-zero exit means something failed.

Metadata (name/difficulty/length/up/down) is a separate, non-automatable step — it doesn't come from the GPX, it comes from whatever official source exists for that region (tourism site scraping for Paznaun; the `BiketrailsNauders.pdf` brochure's S0–S3 scale for 3-Länder's 21 numbered trails). Where no official length/Hm exists (newer trails not in a brochure), GPX-computed length/elevation-gain-loss is an acceptable fallback — but prefer official published numbers over GPX-derived ones when both exist, to stay consistent with the rest of `lineTrails`.

**For `diff` specifically there is a standing rule (user, 2026-08-14): the OPERATOR's own published difficulty always wins.** Trailforks' per-trail rating — convenient because it is consistent across regions and maps 1:1 onto this app's four colours, and the rule Finale Ligure and the Harz were first built to — is the **fallback for trails whose operator publishes no grade at all**, not the default. Two things this needs whenever it is applied to a region: check *every* operator page rather than assuming a park publishes a grade (three of the Harz's six do not, and one publishes coloured trail *markings* that read like grades but are not), and record each trail's operator **wording** next to the colour it maps to, so the mapping stays auditable without re-fetching the pages. A three-step German scale (leicht/mittel/schwer) maps onto the app's own labels — leicht → `blau` ("Leicht"), mittel → `rot`, schwer → `schwarz`, so `gruen` ("Sehr leicht") is simply not reached from that scale — and a grade stated across two steps ("mittel / schwer") takes the **harder** one, the same direction a merged trail's per-section `max()` already rounds in. `tools/build_harz.py`'s `OPERATOR_DIFF`/`resolve_diff` is the worked example, pinned by `tests/python/geomerge.py`. Note this rule has **not** been applied retroactively to older regions (Finale's 61-trail realignment in particular is still Trailforks-based) — do that per region when there is a reason to touch it, not as a sweep.

**Finale Ligure specifically** has its own, more involved sourcing method (Outdooractive GPX download, route-ID extraction, difficulty-rating rules, three hard-learned lessons) — see **`docs/finale-ligure.md`**, read it before adding or correcting any Finale trail.

**Trailforks** (bot-blocked, needs a headless browser workaround) and the **general headless-Chromium-without-root setup** for this sandbox are documented in **`docs/data-sourcing-general.md`** — these apply beyond just Finale.

### Adding a new region under this model

**See `docs/adding-a-region.md` for the full runbook** — the order of operations, the decisions that need the user (difficulties where nothing official exists, the sub-region split, one region or several), and the verification step. In short:

1. Run the pipeline (`tools/trailmap_pipeline.py`) to produce that region's trail data, then shape it into `regions/<newgroup>.json` as `{ lineTrails, trailGeo, elevationProfiles, places }` — `write_region()` does the last part in the app's own formatting.
2. Add one `REGION_CATALOG` entry: `label`, `file`, `trailCount`, a computed `bounds` bounding box (`region_summary()` gives you one), and `subRegions` (label+color per sub-region/hub).
3. `python tools/validate_region.py <newgroup>`, then look at it in a browser against the base map.
4. That's it — no other code changes needed. The dialog, sidebar, `render()`, persistence, and map-fitting all already iterate the catalog/active-state dynamically.

- **A tap on a trail is driven entirely by our own code, never through the platform's own click** (2026-08-04, two passes). First pass fixed a real, measured cause: browsers hit-test a touch's native synthetic `click` at the TOUCHEND position, not the touchstart one, and a normal tap's finger settling a few pixels in between is completely ordinary. On a densely packed map — many short trails' invisible hit-lines close together, worst at a low zoom where a whole region compresses into a small screen area — that drift is often enough to move the click onto a neighbour's start/end dot or onto empty map (measured on Donnersberg's own boot zoom: a realistic 4px settle mismatched 134 of 400 sampled points). But the user could still reproduce the identical symptom after that shipped, on a phone, only at a low zoom — the signature of a SECOND, independent cause: iOS Safari's documented "first tap on a hover-reactive element only applies `:hover`, the click needs a second tap" quirk. Our hit-lines qualify (`mouseover` visibly thickens them), and this has nothing to do with where the finger landed — down can equal up and the native click still just does not fire, which a mismatch-only check can never catch. The fix that closes both at once: stop trusting the platform's click at all for a touch that STARTED on one of Leaflet's own interactive paths. `map.getContainer()` carries one `touchstart`/`touchend` pair (not one of the ~10 places a trail/lift/marker binds its own `click`) that records the touchstart target and, on touchend, unconditionally `preventDefault()`s and dispatches a `click` DOM event on that element — indistinguishable to Leaflet from a real one. Guarded at touchSTART, not touchend: only a touch landing on a path with class `leaflet-interactive` is intercepted at all, so a tap on empty map, a button, or a card is completely unaffected, and a real drag (movement over 14px or 500ms) is left to Leaflet's own dragging untouched. Worth knowing for the next case like this: a scripted `TouchEvent` dispatch never produces the browser's own synthetic click, so the "identical down/up position" reproduction could not even be tested until the app stopped depending on that synthesis — the first version of this fix could only be measured via the positional-mismatch case, not the ghost-tap one.

Switching apps during that half second was enough. `bearingTweenSafety` lands on the target if the frames do not come back; the last frame cancels it when they do. The suite's animation case *skips* rather than fails when it measures fewer than 5 frames in 250 ms, because a window that is not being painted has nothing to say about easing — its arrival checks still run, and they are what proves the safety net.

Diagnosing leaflet-rotate's own internal call graph precisely enough to fix this with more patching was judged not worth the risk a second time.

### Service worker (`sw.js`)

- App shell (`index.html`) is network-first with cache fallback (so updates land while online, offline still works).
- Everything else (Leaflet assets, map tiles) is cache-first, filled in the background.
- Any cache write inside a fetch handler must be wrapped in `event.waitUntil(...)` — without it the browser can kill the service worker before the write completes, silently dropping tiles from the cache (this was a real, previously-fixed bug).
- Tile fetches must use `{mode:'no-cors'}` — public tile servers don't send CORS headers, so a plain same-origin-mode `fetch()` fails silently.
- `sw.js`'s fetch handler itself is generic and needs no changes to support a new region — its cache-first branch already covers `fetch("regions/<groupKey>.json")` the same way it covers CDN Leaflet assets. `APP_SHELL` (precached at install time) intentionally includes only the *default* region (`regions/paznaun.json`), so a first-ever visit works fully offline without precaching every region — that would defeat the point of lazy loading. `CACHE_NAME` in `sw.js` must match `PRELOAD_CACHE_NAME` in `index.html`.
- **`leaflet-rotate.js` is cached exactly like the stylesheet**: cache-first, `?v=` in the URL, `ROTATE_URL` in `sw.js` mirroring the `<script src>` in `index.html`, and in `APP_SHELL` so a first-ever offline visit has it. Bump both together; `tests/python/appshell.py` fails if they disagree.
- **`style.css` is cache-first and versioned in its URL.** Three things must stay in sync on every CSS change: the `?v=` in the `<link rel="stylesheet">` in `index.html`, `STYLE_URL` in `sw.js`, and (since the stylesheet is in `APP_SHELL`) a `CACHE_NAME`/`PRELOAD_CACHE_NAME` bump. The version in the URL is what actually makes a change arrive — `index.html` is network-first, so a new deploy asks for a stylesheet URL the old cache cannot answer. Do **not** switch the stylesheet to network-first instead (tried 2026-07-27, rejected by the user): this app is used offline and on one bar of signal, where that stalls the whole page behind a request timeout. Why it matters more than it looks: if a new `index.html` is paired with an old `style.css`, a newly added element has *no rules at all*, therefore no `position:absolute`, and paints behind `#map` (`position:absolute; inset:0`) — it does not look unstyled, it disappears completely. That is exactly how the pinned Tourenbuilder sheet went missing on the user's phone while everything else looked normal.
