### Trincea/Bormida correction (2026-07-23) — resolved on the 3rd attempt, via a user-supplied GPX

**What went wrong**: "Trincea" was moved into Melogno as one of the "must include" trails above, using the `rz_trincea` entry already built earlier (from the original GPX-centroid-clustering pass into the Ranzi zone, `finaleoutdoor.com/en/trails-walls/trincea-1`). The user then flagged this as wrong: their real "Trincea" is a short trail that ends on the Tagliego (Rialto-Din) route, and OSM calls it something else.

**Root cause**: `trincea-1`'s own official finaleoutdoor.com description says outright it's "a great alternative to the gravel road to reach the highest point of the **Ranzi** trail area" — this is a real, distinct trail that happens to share the name "Trincea" with the one the user meant, and its own coordinates (~44.159, 8.247) are nowhere near the Melogno/Din cluster (~44.19–44.24). **Two different trails, same name, in different parts of the region** — reverted: `region` back to `monte_carmo_ranzi`, `id` back to `rz_trincea`. This part of the correction stands and is correct.

**The "Bormida" hunt — two wrong guesses, then abandoned**: an Overpass search for `name~"Trincea"` near the Din/Rialto cluster turned up an OSM way literally tagged `name=Trincea` (`mtb=yes`, `mtb:scale=2`), but only a tiny ~20 m fragment. The user said to leave that alone and instead name the trail they meant after its own OSM name: **"Bormida"**.
1. **First guess**: "Strada provinciale Osiglia - Bormida - Melogno" (a paved provincial road merely passing near the village of Bormida) — built, then flagged wrong by the user, who attached a map screenshot with the actual intended route highlighted (a forested path, not a road, near Monte Alto/Bricco dei Prati).
2. **Second guess**: an OSM CAI hiking-route *relation*, "Bormida - Quadrivio SP Melogno" (24 member ways chained together) — matched the screenshot's shape reasonably well and was rebuilt from it, but **the user said this was still the wrong "Bormida"** and, given how long this had already taken, asked to just delete the trail entirely rather than keep trying. Done — `melogno_bormida` removed from `finale.json` completely, no replacement.

**Lesson from the two wrong guesses**: two visually-plausible OSM matches in a row were both wrong — for a route the user has ridden and knows precisely, chasing an approximate visual/name match on OSM has a real failure ceiling, and a screenshot alone (without being able to click through and get the exact way/relation ID) isn't always enough to pin down the right feature, even when it looks close. **When a specific correction is taking multiple rounds with no converging signal, stop and ask whether to drop it rather than keep guessing** — the user explicitly said as much here ("Das dauert mir zu lang"). A trail that can't be confidently sourced is better left out entirely than included wrong.

**Third attempt — resolved, via a user-supplied GPX (2026-07-23, later same day)**: after dropping the trail, the user came back with `Material/Finale Ligure/trincea.gpx` — a GPX they exported themselves directly from **mtb.waymarkedtrails.org** (metadata: `<name>Trincea</name>`, `route?id=14866409`) for the route they'd been calling "Bormida/Trincea" all along. Two things worth remembering:
- **This GPX uses self-closing `<trkpt lat=".." lon=".."/>` tags with no separate closing tag** — the project's regex-based GPX parser (`gpx_pipeline2.py`'s `parse_gpx`) only matched the `<trkpt ...>...</trkpt>` form and silently returned **0 points** on this file. Fixed the regex to accept both forms (`(?:/>|>(.*?)</(?:trkpt|rtept)>)`) — worth checking for on any future waymarkedtrails.org export, since that's evidently their default GPX style, different from Outdooractive's own downloads.
- **waymarkedtrails.org exports a route as a single clean track**, already correctly ordered — no relation-chaining needed on this end, unlike the manual OSM-relation work for Bormida-attempt-2 or Ciapin Lodge. This is the most reliable way to get a clean, correctly-ordered GPX out of an OSM route relation: let waymarkedtrails.org (or a similar route renderer) do the relation-assembly, rather than reimplementing it by hand from raw Overpass way data.

Verified against the rest of the map before trusting it: the trail's own start point sits **~42 m from Tagliego (Rialto-Din)'s own line** — directly confirming "ends on the way from Rialto-Din" from the very first message in this saga. Built as `melogno_bormida`: 3.69 km, 262 m up / 125 m down (elevation backfilled via OpenTopoData as usual, since the GPX itself carries no `<ele>` data), `blau` (no explicit difficulty signal available from this source — a plain best guess, given it reads as a moderate connector/approach path, not a technical descent).

**Separately, still valid**: when a trail name collides with an unrelated same-named trail elsewhere in the same region (the original Trincea/Ranzi mix-up), coordinates are the fastest disambiguator — check them against the hub's other trails' known coordinate range *before* trusting a name match, not after building on it.

## Getting GPX: Outdooractive + finaleoutdoor.com

No brochure, no per-trail GPX-download button on the official site. The actual trail data lives on Outdooractive, and GPX is fetchable directly and unauthenticated via:

```
https://www.outdooractive.com/en/download.tour.gpx?i=<routeID>&project=outdooractive
```

(confirmed byte-identical to a manual browser download).

**Finding the route ID:**
1. A `finaleoutdoor.com/en/trails-walls/<slug>` detail page's own HTML often embeds it directly: `curl` the page (needs a real `User-Agent` header — a bare `WebFetch` markdown-conversion misses it) and grep for `conf.id='(\d+)'` inside the page's embedded Outdooractive widget-init script. When present this *is* the route's Outdooractive ID and feeds straight into the GPX-download URL above (confirmed working for "Voltage" and 7 other previously-unobtainable trails found via a fresh `Finale Outdoor Trails.docx` link export). Not every trail page has this (older/lower-traffic pages sometimes have the widget script commented out).
2. When missing, fall back to `WebSearch site:outdooractive.com "<trail name>" finale-outdoor-region`, which reliably surfaces the route's own Outdooractive page (URL pattern `/en/route/mountain-biking/finale-outdoor-region/<currentNumber>-<slug>/<routeID>/`) with its current number, description, and often an explicit S1–S4 difficulty rating in the snippet.
3. Occasionally a curator has published a "Raccolta" (collection/list) page covering a whole hub's trails at once (e.g. searching `site:outdooractive.com "<Hub Name>" raccolta` or list) — when one exists it's a major shortcut (one WebFetch instead of N searches), but don't assume one exists for every hub.
4. Bulk ID-range-probing the download endpoint (checking the `Content-Disposition` filename header) does **not** work reliably — Outdooractive's IDs aren't sequential by hub or trail number, hit rate is very low, and hammering the endpoint this way triggers a `429 Too Many Requests` block (wait ~30–60s and retry once it clears; avoid re-triggering it with more bulk probing).

Prefer an explicit Outdooractive S-rating (S1–S4, shift S1→`blau`, S2→`rot`, S3→`schwarz`, S4→`schwarz` to fit this app's 4-tier scale — confirmed with the user this shift is intentional, Finale's terrain reads harder than the raw label suggests) over reading the 2021 trail-map legend's dot color by eye.

finaleoutdoor.com's own detail pages also carry a genuine (if coarse) difficulty signal: a CSS class list containing `SKILL_FACILE`/`SKILL_MEDIA`/`SKILL_DIFFICILE`/`SKILL_VERYHARD` (Italian: easy/medium/difficult/very-hard) — cross-checked against ~20 known trails: `VERYHARD` reliably means `schwarz`, but `MEDIA`-only and `DIFFICILE`-only each straddle two of our tiers (blau/rot and rot/schwarz respectively) so still need the page's own descriptive text as a tie-breaker, same as the Outdooractive method.

## Three lessons learned the hard way

1. **Trail numbers on Finale's 2021 legend photo are stale and keep shifting** — Outdooractive has renumbered trails at least once since 2021 (e.g. "Ponti Romani" was 1 in 2021, is 2 now). Always match by **name**, never assume a 2021 number still identifies the same trail, and don't assume a trail's neighbors-by-number in 2021 are still its neighbors now (this caused an actual mis-attribution: 6 trails read as "San Bernardino" turned out to still be Le Manie, confirmed by their own Outdooractive descriptions literally saying "access to the Manie plateau").
2. **Don't trust the 2021 photo's dot color for difficulty** — reading it by eye produced multiple confirmed-wrong results once cross-checked against Outdooractive's own stated S-rating (e.g. a trail read as purple/S3 turned out to officially be S2, another read as green/S1 was officially S2). Where no rating turns up in search results, err toward flagging the trail's `diff` as an unconfirmed best guess (note it in a comment) rather than presenting a guess with false confidence.
3. **A row's background color in a scraped/exported list is not automatically a difficulty encoding either** — `Finale Outdoor Trails.docx` (parsed into `Material/Finale Ligure/Finale Outdoor Trails (parsed).md`) has 4 distinct paragraph-shading colors behind each trail name; cross-checked against ~20 trails whose `diff` this app already has confirmed and it does **not** correlate (e.g. DH Men/DH Women, essentially paired sibling trails, have different colors; two trails independently confirmed both `schwarz` also differ). Likewise the same source's embedded `SKILL_*` page tags only weakly correlate (~70%) with this app's confirmed `diff` values and shouldn't be trusted alone.

General rule holding across all three of these: prefer an explicit per-trail official rating (S-rating, or corroborating descriptive/prose text about the trail's character) over any color or tag found in bulk-exported list data — bulk exports are convenient for names/links/stats but not for difficulty.

**Also**: 2021-photo region *boundaries* have proven unreliable twice now (trails that looked like they belonged to one region by their position on the page turned out to belong to the neighboring one, confirmed via the trails' own Outdooractive descriptions) — when adding a hub, verify a trail's hub assignment against descriptive text, don't trust the photo layout.

## Workflow (confirmed working end-to-end, user happy with it as of 2026-07-22)

1. Try Outdooractive GPX via `WebSearch site:outdooractive.com "<name>" finale-outdoor-region`, or check if the trail has a `finaleoutdoor.com/en/trails-walls/<slug>` detail page (the latter's raw HTML often embeds `conf.id='<routeID>'`, which feeds straight into the direct GPX-download URL).

## Trailrunde from a Trailforks ROUTE page (feasibility experiment, 2026-08-09 — reverted)

**Outcome: the user asked to delete the Trailrunde again ("war nur ein Versuch") after the jump-boundary
fix below landed.** The tour itself (`finale_feglino_mtb_prova`, `loop:true`) and its geometry/segments were
removed from `finale.json`, trailCount back to 217. **"Trail del Boccion parte 2" — the one standalone trail
sourced along the way — was kept** (real trail, correctly built, has its own value independent of the tour
experiment). The matching method and its jump-boundary lesson below are kept in this doc for the next time a
route-based Trailrunde is attempted, since that work is what would need reusing, not repeating.

The user asked whether a Trailforks *route* (not trail) page could become an in-app Trailrunde, using
`https://www.trailforks.com/route/feglino-mtb-prova/` ("feglino mtb prova", 43.9 km, E-Bike, 2047 m
climb/-1918 m descent) as the test case. Unlike a single trail page, a route page embeds only **one**
`encodedpath` — the route's own single recorded track — plus a **"Trails in Route"** list of named
stretches with per-stretch distance, but no per-stretch geometry.

**The purple-triangle icon is the filter, not the trail name.** Every row in "Trails in Route" carries a
`dicon_small` difficulty icon exactly like the region table view's own icon (see
[[trailforks-anonymous-polyline-extraction]]); on a route, most rows are `dpurple`/"Access Trail, Road or
Doubletrack" — access/connector stretches the route happens to ride, not real named descents. The user's own
rule, given after seeing the rendered page (the icon is not visible in a plain text extraction — must inspect
the DOM's `[class*="dicon"]` elements and their `title` attribute directly): only the non-purple rows are
"real" trails worth integrating; a purple row is only worth reusing if we *already* have that name as one of
our own trails (regardless of whether it's flagged `uphill`) — otherwise leave it as an anonymous grey
connector built from the route's own track, don't go source new geometry for it.

Applied to this route's 20 rows (13 unique names): **5 non-purple real trails** — Ludi Trail, Variante
Rocche Gianche, Rocche Gianche, Trail del Boccion parte 2, Crestino Pt. 2 — of which only **Trail del Boccion
parte 2** was missing (added as a new `mallare`-region trail, 3.3 km/-444 m, matching the naming/region of
the already-built "Trail del Boccion" part 1). Two purple rows were reused because we already had them as
real trails: **Colla San Giacomo AV** and **Cadotto** (the latter already `uphill:true`). The rest (Feglino-
Carbuta climb, Carbuta-San Giacomo climb, Calice-Carbuta UP, Verso S. Giacomo, Super Groppo Climb, Rocce
Bianche climb) stayed anonymous connectors.

**Matching method**: decode the route's own track (2061 raw points → 678 after an in-browser Douglas-Peucker
simplification, re-encoded and pulled through the browser tool in 400-char slices to dodge its ~1000-char
per-call truncation — a smaller, verifiable chunk size than the trail-page technique's 900-char target, and
explicitly checking each chunk's returned length against the requested slice size, which caught a real
silent truncation on the first attempt: the first "1000-char" pull actually returned fewer characters,
corrupting the decode until re-pulled in 400-char pieces with the length checked every time). For each
candidate known trail, take the minimum haversine distance from every route point to that trail's own
geometry; a contiguous run under ~60 m is the matched window, direction decided by comparing the route
points just outside each end of the window against the trail's own first/last point.

**Rocche Gianche deliberately left unmatched despite a plausible-looking window.** Its candidate window's
distance-to-geometry at the window's *own* start was 636–659 m — nowhere near either of the trail's own
endpoints — while only the tail end sat close (45 m). User reports on the route's own comment thread
independently describe this trail as having "3 sections" of very different character, and the review
thread's own consensus is to bail onto a different trail partway down. Substituting the whole 2.04 km
`schwarz` trail here would draw geometry the route never actually rides (violating the loop's own critical
invariant that `TRAIL_GEO` must exactly equal the segment concatenation — see the Trailrunde doc) — so this
stretch stayed a plain connector instead of a forced substitution, per the project's standing "leave the
honest gap" rule ([[no-silent-auto-corrections]]).

**Known imprecision from the first pass, since fixed (2026-08-09, same day)**: the user reported visible
"jumps" — straight lines cutting across terrain at odd angles — right after Ludi Trail, after Cadotto, and
entering Trail del Boccion parte 2. Root cause: the first pass decided a trail's matched *window* by
proximity to **any** point on the trail's geometry (a 60 m corridor threshold), then cut the connector at
that window's edge — but never checked that the cut point was actually close to the trail's own **endpoint**.
A window can sit well inside a trail's corridor while its edge is still hundreds of metres from where the
trail's stored line actually starts/ends, and substituting the *whole* trail geometry from that wrong edge
produces exactly this: a straight jump from the connector's last real-track point to the trail's own (distant)
endpoint. Measured gaps once diagnosed: 174 m after Ludi Trail, 357 m after Cadotto, 846 m entering Boccion
parte 2.

**The fix**: for every candidate trail, search the *whole* route track for the closest point to that trail's
own `geo[0]` and `geo[-1]` specifically (not "any point in the corridor"), and only keep the trail as a
substituted segment if **both** ends land within roughly 100 m of a real endpoint match. Re-running this over
Ludi Trail exposed why its match was always wrong: the route only ever grazes Ludi's own *starting* junction
(twice, each time diverging onto a different unrelated spur within 3 points, `d=0m` at the junction itself but
150m+ away by the time it would need to reach Ludi's other end) — it never actually rides the trail, so the
"403 m" Trailforks attributes to it in "Trails in Route" doesn't correspond to riding this stored geometry at
all. Excluded entirely; that whole stretch is now a plain connector. Cadotto and Boccion parte 2 both turned
out to be genuinely good matches once anchored to endpoints instead of the corridor: Cadotto's real exit sits
just 23 m from `geo[0]` (not 357 m away), Boccion 2's the same story at both ends (11–105 m, not 846 m).

Rebuilding with these corrected boundaries **also improved the overall length accuracy as a side effect**:
42.6 km built vs. the route's own stated 43.9 km (was 47.1 km before the fix) — removing Ludi Trail's
false ~400 m substitution and tightening every other boundary happened to close most of the earlier
overshoot too, without deliberately chasing that number. `up`/`down` (2047/-1918) stay Trailforks' own
official stats regardless, consistent with `official=` always winning over GPX-derived numbers elsewhere in
this pipeline. This endpoint-anchored check is the one to reuse first on any future route-page Trailrunde,
before trusting a corridor-proximity window at all.

finale.json`), trailCount 216→218 (217 for the tour itself, 218 once Trail del Boccion parte 2 was added as
its own standalone trail entry too — its own `lineTrails`/`trailGeo`/`elevationProfiles` entry, not just a
