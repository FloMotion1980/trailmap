# Does it actually bite?

A suite nobody has watched fail proves nothing. This file records, per suite, **what has been verified** — a
mutation that was applied and reverted, or better, a real bug the suite caught on its first run. It also says
plainly which suites have *not* been mutation-checked yet, so nobody mistakes an untested test for a tested
one.

To verify a mutation: apply it, run the suite, confirm the listed failure, revert. Keep the counts here
current; a stale count is worse than none, because it looks like evidence.

## Verified by catching a real bug (the strongest evidence there is)

| suite | what it found, unprompted |
|---|---|
| `lists` | **A group heading in the trail list claimed 147 above hub headings adding up to 141.** The per-list hub counts had been split off when Tours moved to their own section, but the per-list *group* count still used the trails-and-Tours tally. Check: "the group counts add up to the section count". |
| `lists` | **The selected card lost its highlight on every re-render.** `render()` rebuilds every card, and only the Tour and lift lists re-marked the selected one — the trail list never did. So toggling any filter with a trail selected left the map showing a selection the sidebar denied. Fixed by one shared `reattachSelectedCard()`. Check: "the selection survives a re-render". |
| `pipeline` | **`build_profile` ignored implausible `0 m` elevations** although its own comment claimed to fill them, so a single `<ele>0</ele>` mid-track produced a full-depth dip plus a phantom climb back out. Fixed; the golden Laax rebuild in the same suite proved it changes no committed region. Check: "build_profile interpolates missing and implausible elevations". |
| `appshell` | Corrected a false belief rather than a bug: the `no-cors` rule for tiles lives in `index.html`'s preload, **not** in `sw.js`, where CLAUDE.md's wording had put it. |
| `filters` | Corrected a check that could only pass by luck: "Touren are named separately when some are hidden" matched `/Touren?/`, which demands at least "Toure", while the app correctly writes the singular "1 Tour". It had passed only because the hidden difficulty happened to contain no Tour; in bikekingdom one Tour is schwarz and the case failed against a correct app. A check whose outcome depends on which region's data it meets is worse than no check. |
| `bearing`, `ride`, `lifts` | **Three suites dereferenced `list[0]` on the line after asserting `list.length`** — so the assertion failed and the very next line THREW, and a throw takes the whole suite with it. In `bearing` that was the direction-arrow case reading `arrowPath().getAttribute("d")` after turning the map, where the arrow is genuinely absent for a frame or gone from the view: it aborted roughly every other run, took the six cases below it with it, and left the map mid-turn for whichever suite ran next — which is what the `controls` and `infopanel` "flakes" were. Not three independent problems; one throw's blast radius. All three read through a guard now. |
| `bearing` | **"direction arrow chevrons keep a constant on-screen size across zoom" was measuring the wrong quantity entirely.** A trail's arrows are all sub-rings of ONE polygon, so the element's own `getBBox()` is the extent of the whole trail — 509 px on one Bike Kingdom trail against a 15 px triangle — and comparing THAT across two zooms compares "how much of this trail is on screen", which is roughly stable and made the case look like it was passing. It parses the first ring out of the `d` attribute now, and zooms with `setZoomAround` so the arrow it just measured cannot leave the view (holding the centre and zooming three levels left one in view by luck, and it skipped on two runs of three). |
| `bearing` | **"centring survives a container whose size Leaflet has not noticed yet" was asserting something that cannot be true.** It fabricated the stale size by writing to `map._size` — and under THAT state `invalidateSize`'s compensation `_rawPanBy`s the pane while Leaflet's own `getCenter()` stays put (preserving the centre is the whole point of it), so the pixels are displaced by (+261, −293) while the model says nothing moved, and the animated `panTo` that follows applies a DELTA on the already-displaced pane. Measured, not reasoned about. It asserts the repair now — the size is back, the pill says so — and leaves "the position ends up centred" to the second half of the same case, which changes the container for real. |
| `controls` | **The fold case measured pixels an animation has to move.** `#liveStatusPanel` collapses via a `max-width` CSS transition, which needs animation frames — so in any window that is not being painted the width never changed and the case failed against a correct app. It asserts the `collapsed` class either way now and gates the pixels on `TM.paints()`. |
| `regiondata` | **`donnersberg.json` had lost its entire `trailSegments` key in a rebuild** (commit `b881699`) and stayed that way for several commits, until the user noticed "Wasser & Holz" drawing without any of its component-trail colours. `validate_region.py` checks segment consistency when the key is PRESENT and says nothing at all about one that is gone. Now guarded by a committed per-region count that may only go up. |
| `regions` | **A region activated while "Orte" was off flashed all 17 of its place labels onto the map** before `applyPlaceVisibility()` took them away again a frame later. The count was 0 by the time anything looked, which is why it had never been noticed; the check that caught it sampled mid-fade and read 3. `buildPlaceMarkers` honours the switch at creation now, and the case watches the tooltip pane with a MutationObserver instead of sampling, so it asserts "never added" rather than "gone by now". |
